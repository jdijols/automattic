This PRD specifies the schema, validator, and deterministic assembler that turn a constrained AI intermediate representation into a downloadable, vanilla-WordPress-installable FSE Block Theme `.zip`. It is the contractual gate. Two sentences from `STRATEGY.md` govern everything below:

> **Contractual invariant (not a metric):** 100% catch rate on `<!-- wp:html -->`, hallucinated block names, and invalid `theme.json`. Below 100% is a release-blocking bug, not a degraded number.

> Treat the AI's output as untrusted, schema-validated input to a deterministic theme-assembly pipeline — **the parser, not the prompt, is the gate.**

These are resolved decisions, cited here and not re-litigated. The single most consequential research finding is that **WordPress itself enforces almost none of this at install time** — its block parser is purely structural and never consults the block registry,[^2][^4] and `WP_Theme_JSON::sanitize()` silently drops unknown keys rather than warning.[^11] A hallucinated block name and a malformed `theme.json` both produce a theme that *installs and activates cleanly* and breaks only at edit/render time. The correctness backbone exists precisely because the platform's own gate is permissive.

## 1. Goal

Phase 1 delivers the typed boundary and the deterministic machinery that let Phase 2 (AI Prompt Engineering) begin against a frozen contract. Concretely, Phase 1 is done when all of the following are falsifiably true:

1. **A versioned IR schema exists** (§2) such that, *on the `blockNode` path*, any value the AI can legally emit is, by construction, incapable of expressing the Custom HTML block — there is no node type that carries raw HTML through to output. The `patternRef.params` path is **not** type-excluded: its safety is neutralization-at-substitution (§6.4 per-slot escaping) plus the layer-4 byte scan, not a type guarantee. The `wp:html` invariant is enforced first by the *shape of the type* (for `blockNode`), then by the validator, then by a render gate (defense in depth).
2. **A validator** (§5) accepts an IR value and returns either a typed, assembled artifact or a structured error list — never a silent pass on malformed input. Acceptance test: a corpus of adversarial IRs (hand-written + "AI tried to escape into HTML" fixtures, mandated by `CLAUDE.md`) achieves a 100% catch rate on the three invariant classes.
3. **A deterministic assembler** (§6) maps a validated IR to a byte-reproducible `.zip` — same IR in, same bytes out, on any machine.
4. **An automated install/activate harness** (§7) installs that `.zip` into a clean WordPress and asserts zero activation errors *and* zero `core/missing` blocks *and* zero silently-dropped `theme.json` keys. This is the lagging metric STRATEGY assigns to Track 1: *Vanilla-WordPress install + activate cleanliness rate*, target 100%.[^STRATEGY]
5. **The Track 3 contract is frozen** (§8): the IR schema, the block-name allowlist, and the structured error format are published as the interface Phase 2 codes against.

Non-goals for Phase 1: prompt construction, model choice, retry policy (Track 3 internals); pattern curation and the distinctiveness rubric (Track 2); the input form and error display UI (Track 4). Track 1 names the *contract* these consume, not their implementations. Per the brief's phase budget, the schema/IR/validator land in Phase 1 (4–6h) and the assembler + zip + install harness land in Phase 3 (6–8h); this PRD scopes both because they are one architectural unit. The five goals above split across that budget:

| Goal | Phase | Exit criterion |
|---|---|---|
| 1 IR schema, 2 validator (layers 1–3), 5 frozen contract | **Phase 1** (4–6h) | schema + allowlist/grammar + error format published; layers 1–3 catch the §5.3 corpus |
| 3 assembler + serializer + zip, 4 install/activate harness, validator layer 4 | **Phase 3** (6–8h) | byte-reproducible `.zip`; §7 Playground gate green |

**What Phase 1 guarantees — and what it deliberately does not.** This backbone guarantees *structural* correctness (no `wp:html`, no hallucinated blocks, valid `theme.json`, clean install). It does **not** guarantee *visual* quality — a valid IR can describe a boring theme, and the brief weights distinctiveness ("visually impressive, not generic") heavily. Distinctiveness is Track 2's burden, but Track 1's allowlist + IR shape *bound* it: the ~26-block surface and the pattern-reference model set the ceiling Track 2 fills. That ceiling is a deliberate tradeoff (the strategy sources taste from a curated library, not free generation), and naming it here keeps the §5.3 positive fixtures honest as an early "would a maker ship this?" smoke-test before the contract freezes. **Proportionality note:** the per-PR enforcement of the invariant (curated corpus, the §5 layers, the §7 gate) is Phase-1/3 scope; the heavier hardening it justifies — property-based generators (Q10), the adversarial red-team (Q10), and the schema drift-detector (§3.3) — is Phase-4 / "What I'd Do Next," not the 5-day MVP critical path. The invariant being binary justifies *enforcing* it 100%; it does not justify three independent proof mechanisms inside the MVP budget.

## 2. Intermediate Representation (IR)

The IR is the typed contract between the AI and the pipeline, and the **provider-swappability seam** (`STRATEGY.md`: the integration must be swappable without a rewrite). The AI's job ends when it emits a valid IR; everything downstream is deterministic. The IR's design is the highest-leverage decision in this PRD — its central fork (pattern-composition vs. free block-tree) is resolved to the hybrid in §2.3 (Q1).

### 2.1 What the IR is, structurally

The IR is a JSON document describing a *theme*, not block markup. It carries: theme metadata (slug, title, author, description, target WP version), a design-token set (colors, typography, spacing) that compiles to `theme.json`, and a set of *regions* (templates and template parts) each populated by a tree of block nodes drawn from a closed allowlist (§4).

A block node is the recursive unit:

```jsonc
{
  "block": "core/cover",          // MUST be a member of the allowlist (§4); validated, not trusted
  "attributes": { "dimRatio": 50, "overlayColor": "contrast", "align": "full" },
  "innerBlocks": [
    { "block": "core/heading", "attributes": { "level": 1 }, "text": "Studio Noir" },
    { "block": "core/paragraph", "attributes": {}, "text": "Photography, in the dark." }
  ]
}
```

Text-bearing leaf blocks carry a `text` field (plain string; the assembler escapes and wraps it in the canonical element). Structural blocks carry only `attributes` + `innerBlocks`. Dynamic/void blocks (e.g. `core/post-featured-image`, `core/template-part`) carry `attributes` and no children. The assembler — not the AI — is responsible for turning a node into byte-exact block markup (§6); the AI never writes the `<!-- wp:... -->` delimiters.

### 2.2 What is expressible — and what is structurally impossible

The decisive property: **there is no `rawHtml` node anywhere in the IR, and `core/html` is absent from the allowlist (§4).** A `blockNode` cannot *be* a Custom HTML block, and there is no field whose contract is "raw markup."

Precisely scoped — the type-level guarantee covers the `blockNode` path, not the whole IR, and "no markup field" needs one honest caveat: `text` fields are free strings. The defense there is **neutralization, not prohibition**: the assembler HTML-escapes every `text` field at serialization (matching WordPress's own `save()` behavior for text content), so a `text` of `"<!-- wp:html -->evil<!-- /wp:html -->"` serializes to escaped entities (`&lt;!-- wp:html --&gt;…`) and renders as the literal visible string — it is *not* parsed as a block. This is correct and lets a user legitimately write a blog post *about* the Custom HTML block. The §5.1 layer-4 scan then looks for **raw, unescaped** `<!-- wp:html` / `<!-- wp:core/html` byte sequences in the assembled output; because every `text` field is escaped, any such raw sequence can only be a real delimiter the assembler emitted — so the scan does not false-positive on legitimately-escaped content, and any genuine escape fails the build.

So the accurate claim is **"structurally excluded at the IR type level for `blockNode`, neutralized for `text`, and re-enforced at validation (layer 4) and at the §7 render gate"** — three independent layers, the first of which makes the dangerous shape unrepresentable rather than merely unlikely. The `patternRef` path (§2.3) is *not* type-excluded — its `params` are validator-and-assembler-dependent (see §6.4); that path's safety is owned by §5/§6, not the type.

Expressible: a query loop over posts with a featured image, title, excerpt, and pagination —

```jsonc
{
  "block": "core/query",
  "attributes": { "queryId": 0, "query": { "perPage": 6, "postType": "post" } },
  "innerBlocks": [
    { "block": "core/post-template", "attributes": {}, "innerBlocks": [
      { "block": "core/post-featured-image", "attributes": { "isLink": true } },
      { "block": "core/post-title", "attributes": { "isLink": true, "level": 2 } },
      { "block": "core/post-excerpt", "attributes": {} }
    ]},
    { "block": "core/query-pagination", "attributes": {}, "innerBlocks": [
      { "block": "core/query-pagination-previous", "attributes": {} },
      { "block": "core/query-pagination-next", "attributes": {} }
    ]}
  ]
}
```

This is the "sophisticated block usage (Query Loop patterns)" the brief's *raises-the-bar* criteria reward — and it is fully native, no HTML block.

NOT expressible (by design): an arbitrary `<section>` with a hand-authored CSS grid; a `<script>` tag; a third-party block not on the allowlist; any attribute key not in the per-block attribute schema (§4). Each of these is either unrepresentable in the type or rejected by the validator.

### 2.3 Curated-pattern composition vs. free block-tree authoring

`STRATEGY.md` resolves the *source of taste*: "source distinctive visual quality from a curated library of designer-grade block patterns the AI composes and parameterizes — the pattern library, not the model's imagination." This pulls the IR toward a **pattern-reference node** — the AI says "use the `hero-centered` pattern with these tokens" rather than authoring the hero's block tree from scratch. Extendify's shipping architecture is exactly this: the AI selects and parameterizes pre-validated patterns and never writes raw markup, which is the only prior-art approach observed to reliably avoid invalid output.[^41] Track 2 owns the pattern library; Track 1 must expose an IR node that *references* a pattern by slug and supplies its parameters. But patterns will not cover every region, so the IR must *also* support a constrained block-tree for the gaps.

**Q1 RESOLVED → hybrid (pattern-reference nodes + constrained free-tree for gaps).** Q1 was previously blocked on "the Track 2 pattern-catalog contract"; that contract now exists in seed form ([`docs/pattern-library/`](pattern-library/) + [`IR-notes.md`](pattern-library/IR-notes.md)), and authoring three real patterns produced direct evidence for the hybrid: each pattern's `meta.json` splits its surface into a `parameterizable` slot set (content, tokens) and a `locked` structure, which is exactly the "pattern reference + slot assignments" model — the AI picks `hero-cover` and fills its declared slots, it does not restructure the cover→group→heading nesting. Free block-tree authoring (Q1 option A) reintroduces the hallucination surface the strategy exists to remove, and `STRATEGY.md` explicitly rejects "freeform AI layout authoring." So the IR commits to the hybrid: `patternRef` is the default authoring mode for covered regions; the constrained `blockNode` free-tree is reserved for gaps the library does not cover. What remains open is *governance* — when the AI is permitted to drop to a free-tree vs. forced to a `patternRef`, and the first-try-success cost of each — which is a Track 3 prompt-tuning concern, not an IR-shape decision. The schema shape (§2.4) is therefore genuinely frozen; only the authoring-mode policy is still being tuned.

> **Decision log (2026-05-27):** Q1 = hybrid. Evidence: the three Track 2 seed patterns demonstrate the pattern-reference + declared-slot model; `STRATEGY.md` rejects freeform layout authoring; `IR-notes.md` §4 independently recommends option C. Residual (Track 3, not Track 1): the policy governing when free-tree is allowed vs. a pattern is forced. This resolves the "frozen contract vs. unresolved Q1" tension — the `oneOf[blockNode, patternRef]` shape is committed; the dial is governance, which does not change the schema.

### 2.4 Formal IR schema (the typed contract Track 3 codes against)

The IR is defined as JSON Schema (the publishable, provider-agnostic artifact §8.1 names) and mirrored as a host-language type for the assembler. Schema below in abridged JSON-Schema form; `$defs` elided for the attribute schemas (those are generated per-block from the allowlist, §4.2):

```jsonc
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://<product>/ir/v1.json",
  "type": "object",
  "required": ["irVersion", "theme", "tokens", "regions"],
  "additionalProperties": false,
  "properties": {
    "irVersion": { "const": 1 },                       // IR contract version — see Q8
    "theme": {                                          // → style.css headers + theme.json title/slug
      "type": "object",
      "required": ["slug", "title"],
      "additionalProperties": false,
      "properties": {
        "slug":  { "type": "string", "pattern": "^[a-z][a-z0-9-]{1,39}$" },  // validated input (brief)
        "title": { "type": "string", "minLength": 1, "maxLength": 120 },
        "author": { "type": "string", "maxLength": 120 },
        "description": { "type": "string", "maxLength": 280 },
        "wpVersionTarget": { "const": "6.6" }           // pins serializer + theme.json schema (§3.2, §6.2)
      }
    },
    "tokens": { "$ref": "#/$defs/designTokens" },       // → theme.json settings/styles (§3, and Q7)
    "regions": {                                        // templates + parts the assembler writes
      "type": "array",
      "items": { "$ref": "#/$defs/region" },
      "minItems": 1
    }
  },
  "$defs": {
    "region": {
      "type": "object",
      "required": ["kind", "name", "content"],
      "additionalProperties": false,
      "properties": {
        "kind": { "enum": ["template", "part"] },
        "name": { "enum": [                             // closed set — no arbitrary filenames
          "index", "single", "archive", "page", "home", "404",  // templates
          "header", "footer"                                    // parts
        ]},
        "content": {
          "type": "array",
          "items": { "$ref": "#/$defs/node" }
        }
      }
    },
    "node": {                                           // the recursive block unit (see Q7)
      "oneOf": [
        { "$ref": "#/$defs/blockNode" },
        { "$ref": "#/$defs/patternRef" }                // Q1 hybrid: reference a Track 2 pattern
      ]
    },
    "blockNode": {
      "type": "object",
      "required": ["block"],
      "additionalProperties": false,
      "properties": {
        "block": { "$ref": "#/$defs/allowedBlockName" },// enum of the §4.1 allowlist — NOT a free string
        "attributes": { "type": "object" },             // per-block schema applied in validation layer 2
        "text": { "type": "string", "maxLength": 2000 },// leaf text; HTML-escaped by assembler; capped (resource-exhaustion bound)
        "innerBlocks": {
          "type": "array",
          "maxItems": 32,                                // per-node fan-out bound (resource-exhaustion)
          "items": { "$ref": "#/$defs/node" }           // ← recursion point
        }
      }
    },
    "patternRef": {
      "type": "object",
      "required": ["pattern"],
      "additionalProperties": false,
      "properties": {
        "pattern": { "type": "string", "pattern": "^[a-z][a-z0-9-]{1,39}$" }, // slug; existence checked vs Track 2 catalog; pattern-constrained for zip-slip safety (§6.4)
        "params": { "type": "object" }                  // slot assignments: token refs + text; validated/escaped per §6.4 before substitution
      }
    },
    "allowedBlockName": { "enum": ["core/group", "core/columns", "/* …§4.1 list… */"] }
  }
}
```

Three properties of this schema are load-bearing:

1. **`additionalProperties: false` everywhere** — an AI cannot introduce a `rawHtml`, `customCss`, or `shortcode` field by inventing a key; the schema rejects unknown properties at layer 1 (§5.1). Combined with `block` being an `enum` (not a `string`), the §2.2 "structurally impossible" claim is now mechanical, not aspirational.
2. **`block` is an `enum`, not a pattern-validated string.** A hallucinated name fails schema validation immediately — it never reaches the block-tree layer. The allowlist is compiled *into* the IR schema, so the two stay in lockstep (one source of truth, §4.1).
3. **`node` is `oneOf[blockNode, patternRef]`** — the Q1 hybrid is encoded directly: any slot that accepts a block also accepts a pattern reference, and the validator resolves `patternRef.pattern` against the Track 2 catalog.
4. **Size and depth are bounded.** `text` is capped (`maxLength`), `innerBlocks` is capped (`maxItems`), and the §5 layer-1 validator enforces a maximum nesting depth (≤10) and total node count *before* per-node processing. Without these, a billion-laughs-style deeply-nested IR or a megabyte-scale `text` field — reachable from the public input path, and not constrained at generation time under the Q7 option-C best-effort tree — would exhaust the validator's stack, balloon the `.zip`, or time out the §7 gate. This is a resource-exhaustion (DoS) bound, not a correctness invariant, but it lives in the schema because the recursive shape is where the exposure originates.

The recursion at `blockNode.innerBlocks → node` is where the IR collides with structured-output mechanisms — **OpenAI Structured Outputs forbids recursive schemas and caps nesting at 5 levels,[^29] and Anthropic strict tool use forbids recursive schemas outright.[^31]** A block tree is unavoidably recursive and routinely exceeds 5 levels (cover → group → columns → column → group → heading). So the *full* IR cannot be enforced by constrained decoding; the recursive core must be handled by post-hoc validation (§5) or a non-recursive encoding. This is **Q7** — and it is the first hard constraint that bites the provider-swappability seam, because the seam assumed any provider's structured-output mode could target the IR (§8.1).

**Sub-surfaces the schema above abridges (from [`IR-notes.md`](pattern-library/IR-notes.md), authoring the seed patterns surfaced these — fold into the concrete Zod schema):**

- **Node kind: `static` vs. `template-region`.** A hero subtree renders once; a `core/post-template` subtree renders *per post* against N posts. The schema must distinguish them so the assembler knows which subtrees are templates applied per-item (query loop, comment loop) vs. authored-once. Today this is implicit in containment (`post-template` inside `query`); IR-notes recommends making it an explicit node-kind.
- **Tokens are *references*, not values.** Every color/font/spacing in the patterns is `var:preset|…`, never a literal. The IR carries a token *reference* (slot → vocabulary slug, e.g. color `base`); `theme.json` carries the *definition* (`base = #FFFFFF`, the AI's per-vision choice). The validator must reject a dangling reference — a `var:preset|color|brand` with no `brand` in the palette is invalid-but-parseable, exactly the silent-failure class this backbone exists to catch.
- **Query config is a typed sub-object.** `core/query`'s `query` carries `perPage / orderBy / order / postType / inherit` — a bounded enum/int surface, not free content. Modeled as a typed sub-object the AI fills within bounds (range-checked like §4.2 attributes).
- **Style-variation references.** `is-style-outline` (button), `is-style-logos-only` (social-links) name style variations the theme must register. The IR's vocabulary includes named variations, validated against the set the assembler registers.

## 3. `theme.json` schema

### 3.1 Sourcing strategy — RESOLVED (decision log below)

**Decision:** Vendor the canonical upstream schema as a build-time dependency and validate against it with a standards-compliant JSON Schema validator. Do **not** hand-author a `theme.json` schema fragment, and do not generate one from `theme-i18n.json`.

Rationale: the canonical machine-readable schema already exists at `schemas/json/theme.json` in the Gutenberg repo (mirrored to `https://schemas.wp.org/trunk/theme.json`), is ~94 KB / 3,300+ lines enumerating 100+ blocks, and is authored in **JSON Schema draft-07** — directly consumable by AJV with no translation.[^8] Hand-authoring a subset re-derives work WordPress already maintains and guarantees drift; generating from `lib/theme-i18n.json` is a category error — that file is an i18n key map (which leaf strings are translatable), not a structural schema, and `schemas.wp.org/trunk/theme-i18n.json` does not even serve JSON.[^27] Note draft-07, *not* 2020-12: this dictates validator configuration (§5) and rules out code-first validators that target only their own DSL.

> **Decision log (2026-05-27):** theme.json schema source = vendored upstream `schemas/json/theme.json` (draft-07), pinned by commit. Alternatives rejected: hand-authored fragment (drift, redundant), generate-from-i18n (wrong artifact). Evidence: the upstream schema is draft-07 and consumable as-is.[^8][^27]

### 3.2 Version target

Emit `version: 3` and validate against the matching schema (`trunk` or `wp/6.6`).[^7][^10] Pinning the *pair* matters: the schema file pins `version` per release (`"version": { "const": 3 }` in trunk; `enum: [3]` in `wp/6.6`), so validating a `version: 2` document against the trunk schema **fails** even though WordPress 6.6 runs a v2 file happily.[^8] v3 (WP 6.6) introduced a breaking change to default-preset override behavior: custom font-size or spacing presets that reuse a core slug are silently dropped unless `settings.typography.defaultFontSizes` / `settings.spacing.defaultSpacingSizes` are set to `false`.[^10] The assembler must emit those flags whenever the design tokens reuse core slugs — a §6 assembler responsibility, surfaced here because it is a `theme.json`-correctness concern.

### 3.3 Drift strategy

WordPress ships new schema versions roughly per minor release.[^9][^10] The vendored schema is pinned by commit SHA and bumped deliberately, never floated. A scheduled CI job fetches `schemas.wp.org/trunk/theme.json`, diffs it against the pinned copy, and opens a PR on change — the maintainer decides whether to adopt. Because `WP_Theme_JSON` silently migrates older `version` values up and silently drops unknown keys,[^11] there is no runtime signal that the schema has drifted; the diff job is the only drift detector. This is the cost of WordPress's permissive runtime, paid in CI rather than at the user. (Per the §1 proportionality note, the *automated* drift job is "What I'd Do Next"; the MVP simply pins by commit — a manual bump suffices for a 5-day submission against a fixed WP target.)

## 4. Block-name allowlist + block-tree grammar

### 4.1 The allowlist is the heart of the invariant

The block-name regex WordPress accepts is `^[a-z0-9-]+/[a-z0-9-]+$` (or the un-namespaced core short form),[^25] and `getBlockType(name)` returns `undefined` for any name not in the registry.[^26] Critically, the *serialization parser does not call this* — it tokenizes by scanning comment delimiters and accepts any well-formed name, real or hallucinated.[^2][^4] So a name like `core/hero-section` (does not exist) round-trips through parse/serialize without error and surfaces only as `core/missing` in the editor.[^5] **The allowlist is therefore ours to own and enforce; WordPress will not do it.**

MVP allowlist (closed set; expansion is a deliberate PR, never a runtime fallback):

- **Layout/structure:** `core/group`, `core/columns`, `core/column`, `core/cover`, `core/spacer`, `core/separator`, `core/buttons`, `core/button`
- **Content leaves:** `core/paragraph`, `core/heading`, `core/image`, `core/list`, `core/list-item`, `core/quote`
- **Site/FSE blocks:** `core/site-title`, `core/site-logo`, `core/site-tagline`, `core/navigation`, `core/social-links`, `core/social-link`, `core/template-part`
- **Query loop family:** `core/query`, `core/post-template`, `core/post-title`, `core/post-featured-image`, `core/post-excerpt`, `core/post-date`, `core/query-pagination`, `core/query-pagination-previous`, `core/query-pagination-numbers`, `core/query-pagination-next`, `core/query-no-results`

This list is the union of the [pattern-library](pattern-library/README.md) "de-facto allowlist" (the blocks the three seed patterns actually use) and must stay reconciled with it — the §5.3 positive corpus installs those patterns, so any block they use that is missing here is a hard schema-validation rejection (§2.4 makes `block` an enum compiled from this list). `core/social-links`/`core/social-link` and `core/query-pagination-numbers` were added in iteration 7 to close that drift. *Candidate additions for distinctiveness* (not yet in the seed patterns, flagged by the product-lens review): `core/media-text` and `core/gallery` — common in editorial/portfolio layouts (the photographer-portfolio archetype in §5.3 likely needs them). Deferred pending a Track 2 pattern that uses them, since each addition carries the per-block cost in §4.2 + §6.2.

Explicitly **excluded** (with reasons): `core/html` (the disqualifying block — never on the list under any flag); `core/shortcode` (arbitrary PHP execution surface, escape hatch); `core/freeform` (classic-editor raw HTML); any third-party namespace (not guaranteed present in vanilla WP, violates the standalone constraint).

### 4.2 Block-tree grammar

Beyond name membership, the IR is validated against a *containment grammar*: which blocks may nest in which. A flat allowlist permits structurally nonsensical trees (a `core/column` at template root) that install but render broken. The grammar is a per-block spec of allowed parents/children plus a per-block attribute schema. This is where most "valid name, invalid placement" defects are caught — the same defects that produce `core/missing` or block-invalidation in the editor (§6.2) with zero install warning.

The grammar mirrors WordPress's own `parent` / `ancestor` / `allowedBlocks` block-API constraints,[^43] which core enforces only in the editor inserter — not at parse time — so we re-encode them as a pre-package gate. MVP containment rules (the `*` rows are the constrained ones; unlisted blocks default to "any flow content as child, any container as parent"):

| Block | Allowed parent (constraint) | Allowed children |
|---|---|---|
| `core/column` * | `core/columns` only | any node |
| `core/columns` | any container | `core/column` only |
| `core/post-template` * | `core/query` only | post-context leaves (`core/post-title`, `core/post-featured-image`, `core/post-excerpt`, `core/post-date`) |
| `core/query-pagination-previous`/`-next`/`core/query-pagination-numbers` * | `core/query-pagination` only | none (void) |
| `core/query-pagination`, `core/query-no-results` * | `core/query` only | flow content |
| `core/post-title`/`-excerpt`/`-date`/`-featured-image` * | inside a `core/query`→`core/post-template` subtree (ancestor constraint) | none / void |
| `core/button` * | `core/buttons` only | none (text leaf) |
| `core/list-item` * | `core/list` only | inline content |
| `core/site-title`/`-logo`/`-tagline`, `core/navigation` | header/footer parts or any container | none / void |

Per-block **attribute schemas** bound the `attributes` object (layer-2 validation, §5.1): each MVP block has an allowed-key set with types and, where it matters for correctness, value constraints — e.g. `core/heading.level ∈ {1..6}`, `core/columns.align ∈ {wide, full}` (or absent), `core/cover.dimRatio ∈ [0,100]`, `core/query.query.postType` ∈ the registered post-type list. An unknown attribute key or out-of-range value is rejected, because WordPress will silently drop or mis-render it (the §2.4 / §3 silent-drop hazard applies to block attributes too). **URL-valued attributes** (`core/social-link.url`, `core/button.url`, `core/image.url`/`href`) get an extra safe-scheme check in the overlay — allowed: `https:`, `http:`, `mailto:`, `tel:`; a `javascript:`/`data:` scheme is rejected (the stored-XSS vector in §6.4), since `block.json` types these as a plain `string` with no scheme constraint.

**Attribute-schema sourcing (Q8 RESOLVED): extract the key/type surface from core `block.json` at build time, plus a thin hand-authored overlay for correctness-critical value ranges.** Each core block ships a `block.json` declaring its `attributes` with types.[^44] Confirmed by inspection: `core/heading`'s `block.json` (pinned commit) declares `attributes` with types — `content: rich-text`, `level: {"type":"number","default":2}`, `placeholder: {"type":"string"}` — but carries **no min/max** on `level`.[^45] So `block.json` gives the authoritative key/type surface for free and refreshes by bumping the pinned Gutenberg version alongside the theme.json schema (§3.2/§3.3), but the value ranges that actually matter for the catch invariant (`level ∈ 1..6`, `dimRatio ∈ 0..100`) are *not* in `block.json` and must live in a small hand-authored overlay keyed by block+attribute.

> **Decision log (2026-05-27):** attribute-schema source = extract keys/types from core `block.json` at build time + hand-authored value-range overlay. Alternatives rejected: hand-author everything (redundant with `block.json`, drift-prone), live-WP introspection (needs a booted WP just to emit schemas, overlaps §7). Evidence: `core/heading` `block.json` carries typed attributes but no value ranges.[^45] Risk accepted: the overlay must be maintained for correctness-critical ranges; it is small (only attributes with bounded domains) and covered by the §5.3 fixture corpus.

### 4.2.1 Validation authority — RESOLVED (Q3)

Specifying our own containment grammar settles Q3: the **fast inner gate is a standalone allowlist + grammar parser that we own**, not a dependency on `@wordpress/blocks`' editor-side registry. Rationale: the registry-backed `getBlockType`/`validateBlock` path assumes a hydrated browser-ish block registry and a JS runtime,[^26] couples Track 1 to one language, and still would not give us the *containment* checks (core enforces those only in the inserter[^43]). A standalone grammar is language-portable, fast (milliseconds, no WordPress boot), and is the natural home for the rules we must author anyway. The **§7 Playground/PHP `parse_blocks()` pass is the authoritative outer backstop** — it catches anything our grammar's fidelity misses. Per [ADR-0001](adr/0001-application-stack.md) the language is Node/TS, so vendoring `@wordpress/block-serialization-spec-parser` for *tokenizing* (not validation) is available — but the allowlist + containment + attribute checks are ours.

> **Decision log (2026-05-27, v1):** validation authority = standalone allowlist + containment grammar (fast inner gate) + Playground `parse_blocks()` (authoritative outer backstop, §7). Alternatives rejected: registry-backed `@wordpress/blocks` as primary (language lock-in, no containment coverage, runtime weight), Playground-as-only-gate (too slow for the inner loop, conflates fast/slow gates). Risk accepted: our grammar can drift from core's block-API constraints; the §7 backstop and a fixture corpus (§5 acceptance test) bound the risk. Surfaced in its place: **Q8**.

### 4.3 Rejection of unknown / hallucinated names

Validation walks the IR tree; for every node, `block ∉ allowlist → reject` with a structured error naming the offending node path. There is no "unknown block → pass through" branch — that branch is the invariant violation. The §7 render gate is the backstop: even if a name slipped through (it cannot, given §4.1), Playground asserts zero `core/missing` blocks post-activation.[^22]

## 5. Validator architecture

### 5.1 Layered, ordered, fail-closed

Validation is **per-layer with a fixed order**, each layer a pure function `input → Result<output, Error[]>`. Order matters: cheap structural checks gate expensive ones, and each layer's output is the next layer's input.

1. **IR schema validation** — the AI's output is parsed and validated against the IR schema (§2). Malformed JSON or a node missing required fields fails here. Per the now-Accepted [ADR-0001](adr/0001-application-stack.md), the validator is **Zod** — the same schema the Vercel AI SDK's `generateObject` consumes, so the contract the AI targets and the contract the validator enforces are one artifact (see the Q7 caveat in §8.1 for the recursive part). Language hedging in earlier drafts ("if Node / if Python") is resolved by the ADR: Node 20+/TypeScript.[^37]
2. **Block-tree validation** — every node's `block` is checked against the allowlist (§4.1) and the containment grammar + attribute schema (§4.2). This layer owns the "hallucinated block name" invariant.
3. **`theme.json` validation** — the design tokens are compiled to a `theme.json` object and validated against the vendored draft-07 schema (§3) using AJV — the only mainstream JS validator that consumes an externally-authored schema as-is; `ajv-formats` supplies `uri`/`color` formats.[^36] This layer owns the "invalid `theme.json`" invariant.
4. **Assembled-artifact validation** — after assembly (§6), every serialized region (`templates/*.html`, `parts/*.html`, **and** `patterns/*.php` bodies) is scanned for `wp:html` and `wp:core/html` and re-parsed to confirm names still resolve to the allowlist. This layer owns the "`wp:html`" invariant and catches any assembler-introduced regression. **Three locations must be scanned, not just templates** — pattern bodies carry the same markup and the same risk.[^18]

The `wp:html` check runs at layer 4 as a final byte-level scan even though the IR makes it structurally impossible at layer 1 — defense in depth, because the invariant is release-blocking and cheap to re-verify.

**Layer 2 has two passes, not one** (from [`IR-notes.md`](pattern-library/IR-notes.md) §6 — the seed patterns proved a single pass is insufficient): **(2a) per-node/per-pattern structural validation** — allowlist membership, containment, attribute schemas, and (for a `patternRef`) that the referenced pattern's own structure is intact; and **(2b) post-composition document validation** — invariants no single node or pattern can guarantee alone, only the assembled page can: exactly one `h1` per page (the hero owns `level:1`, everything else `h2`+), heading-outline sanity, and region uniqueness (one hero, one footer). These catch different failure classes — a tree can be locally valid at 2a (every block allowed, every nesting legal) yet violate 2b (two `h1`s from two patterns), so both passes are required.

### 5.2 Structured error format — the dual-consumer contract

A validation failure returns a list of typed errors, each:

```jsonc
{
  "code": "BLOCK_NOT_ALLOWED",          // stable machine code
  "layer": "block-tree",                 // which validation layer
  "path": "templates/index.html › core/query › core/scroll-spy",
  "message": "Block 'core/scroll-spy' is not in the allowlist.",
  "hint": "Use core/query with core/post-template for post lists.", // optional, retry-oriented
  "invariant": "hallucinated-block-name"  // tags the three invariant classes when applicable
}
```

This format is a **Track 1 deliverable consumed by two parties** (`STRATEGY.md`): Track 3 (the orchestrator) parses `code`/`path`/`hint` to construct a retry re-prompt; Track 4 (the UI) renders `message` legibly to the persona — "not raw JSON Schema violations." The format must therefore carry both machine structure and human-legible text; a bare boolean or a raw AJV error dump fails both consumers.

The field set is now **frozen** (Q4 resolved): `code` (stable enum), `layer`, `path`, `message`, `invariant` (nullable), and an optional bounded `hint` are the contract; raw validator internals (AJV error objects, schema diffs) are never included (§8.3). `code` is a closed enum so Track 3 can branch deterministically and Track 4 can map codes to localized copy; `hint` is capped (≤200 chars, no schema fragments) so it can steer a retry without leaking internals.

### 5.3 Acceptance: the adversarial fixture corpus

The 100% catch invariant (§1) is only as credible as the test that proves it. `CLAUDE.md` mandates "AI tried to escape into HTML" fixtures; this section specifies the corpus that turns the invariant from a claim into a CI gate. The corpus is a set of `(input IR or raw model output, expected outcome)` pairs, organized by the three invariant classes plus a must-pass positive set:

- **`wp:html` escapes**: two distinct expected outcomes, per the §2.2 type-vs-text distinction. **Must reject:** a `core/html` node in the IR (type-excluded — fails schema layer 1); a `patternRef` whose resolved pattern body contains `wp:html` (§6.4); raw `<!-- wp:html` surviving to assembled output (layer-4 scan, incl. `core/` prefix and whitespace/casing tricks `<!--wp:html-->`, `<!--  WP:HTML  -->`). **Must neutralize (pass validation, render as literal, layer-4 finds no raw delimiter):** a `text` field containing `"<!-- wp:html -->evil<!-- /wp:html -->"` or raw `<script>`/`<div>` — these are HTML-escaped at assembly and render as visible text (the "blog post *about* the Custom HTML block" case), proving the defense is neutralization, not blanket rejection (§2.2). A fixture that asserted *rejection* of escaped text would wrongly forbid legitimate content.
- **Hallucinated block names** (must reject): plausible-but-fake names (`core/hero`, `core/scroll-spy`, `core/testimonial`); real blocks outside the allowlist (`core/embed`, `core/shortcode`); valid name in an invalid position (a `core/column` at region root — the §4.2 containment case); unknown attribute keys and out-of-range values (`heading.level: 7`).
- **Invalid `theme.json`** (must reject): unknown top-level key; `version: 2` against the v3-pinned schema; a setting key with a typo (`colour`); a malformed color value; a custom preset reusing a core slug without the §3.2 default-disable flag.
- **Positive set** (must pass + install clean): a representative theme per site archetype (blog, photographer portfolio, landing page) exercising query loops, cover heroes, columns, navigation, and template parts — these run the full pipeline through the §7 Playground gate and assert *zero* errors.

Each negative fixture asserts not just rejection but the **exact `code` and `invariant` tag** (§5.2), so a regression that changes *which* error fires is caught too. The corpus is the falsifiable form of "below 100% is a release-blocking bug" — a single uncaught negative fails CI.

**Proving the invariant against *unseen* escapes (Q10 RESOLVED):** the curated corpus alone only proves catches for escapes we imagined, but the invariant claims *all* escapes. The resolution is layered, and the layers are *phased* (per the §1 proportionality note): **(1) the curated corpus is the deterministic per-PR gate — the MVP scope** (it also satisfies the brief's unit/integration-test mandate); (2) **property-based tests** assert the invariant as a checkable property — "no validator result that passes contains `wp:html`, an unregistered block, or invalid `theme.json`" — over generated/mutated IRs, catching *classes* of escape rather than instances; (3) a periodic **adversarial-generation red-team** points Track 3's actual model at "smuggle raw HTML past the validator" out-of-band, every near-miss folded back into the corpus. **Layers 2–3 are Phase-4 / "What I'd Do Next," not the 5-day MVP** — layer 3 is sequentially blocked on Track 3's model existing anyway. This converts the invariant from "we catch what we listed" toward "we catch what the property forbids." **MVP-scope honesty:** at corpus-only MVP scope the 100% claim is provable *as a universal* only for the raw-delimiter (`wp:html`) class — the layer-4 byte scan (§5.1) is a near-universal check for it. For the hallucinated-block-name and invalid-`theme.json` classes, MVP coverage is bounded by the enumerated corpus; the universal arrives with the Phase-4 property layer. Read the §1 invariant as "100% on the enumerated classes, with universal coverage of *unseen* escapes landing in Phase 4" — not as a corpus-only universal, which §5.3 itself rejects as "coverage = imagination."

> **Decision log (2026-05-27):** invariant proof = curated corpus (per-PR) + property-based tests over the §5.1 layers + periodic adversarial red-team feeding findings back. Alternative rejected: curated-corpus-only (coverage = imagination, cannot substantiate a universal claim). Risk accepted: property generators need careful design to produce *interesting* malformed inputs; the curated corpus is the floor if generators are weak. Open sub-decision deferred to implementation: per-PR (seeded, deterministic) vs. nightly fuzzing — not architectural.

## 6. Deterministic assembler

### 6.1 IR → theme files → `.zip`

The assembler is a pure function from validated IR to a file tree, then to a `.zip`. It emits the minimum valid block theme plus whatever the IR specifies:

- `style.css` with the required headers (`Theme Name`, `Author`, `Description`, `Version`, `Requires at least`, `Tested up to`, `Requires PHP`, `License`, `License URI`, `Text Domain`).[^17] `Theme Name` is the floor for WordPress to recognize the directory at all.[^19]
- `templates/index.html` — the *only* file that makes `wp_is_block_theme()` return true; use `templates/`, never the legacy `block-templates/`.[^12]
- `theme.json` (compiled from design tokens, §3).
- Optional templates (`single.html`, `archive.html`, `page.html`, `404.html`), `parts/*.html`, and `patterns/*.php` as the IR specifies — all falling back to `index.html` through the template hierarchy.[^14]

Block markup is produced by a serializer that mirrors WordPress's canonical output: core blocks emitted **un-namespaced** (`<!-- wp:paragraph -->`, never `wp:core/paragraph`),[^6] void blocks in the self-closing form (`<!-- wp:template-part {"slug":"header","tagName":"header"} /-->`),[^16] attributes as JSON in the opening delimiter. The serializer is the sole writer of delimiters — the AI never touches them.

### 6.2 Block-invalidation avoidance — Q6 RESOLVED

WordPress re-runs each block's `save()` on editor load and byte-compares against stored markup; a mismatch marks the block invalid ("this block contains unexpected or invalid content") even though the theme installed fine.[^5] To avoid this the serializer must match core's `save()` output byte-for-byte: correct `wp-block-*` and alignment classes, attribute ordering, no stray whitespace. This output drifts across WordPress/Gutenberg releases, so the serializer is **pinned to a target WP version** and the §7 harness runs against that version.

**Decision (Q6): the bulk of output arrives as pre-serialized pattern blobs; only the small free-tree gap-filler set is serialized from attributes, verified against the JS `save()` oracle.** The "valid but looks broken" failure — recovery banners on every block — directly damages the *install/activate cleanliness* metric and the persona's first impression, the whole JTBD. The original framing here ("verify each block against core's `serialize_block()`") was **wrong about the oracle** and the review caught it: PHP `serialize_block()` only re-wraps already-stored `innerHTML` with the delimiter — it does *not* regenerate a block's inner markup from attributes. The markup WordPress actually byte-compares on editor load is produced by each block's JS `save()` in `@wordpress/block-library`, including conditional classes (`has-background-dim-N`), color-class derivation, and the style-engine's `var:preset|x|y → var(--wp--preset--x--y)` transform. Reproducing that from attributes for every block is a partial reimplementation of `@wordpress/block-editor` — a sub-project, not "26 simple wrappers."

The hybrid (Q1) makes this tractable by *avoiding most of it*: covered regions arrive as **hand-authored, already-byte-correct `pattern.html` blobs** (the Track 2 pattern library), and the assembler does **token/slot substitution** into them, not tree-serialization. So byte-parity is only needed for the small set of leaf/container blocks the free-tree gap-filler emits, and the parity oracle is the **JS serializer** (`@wordpress/blocks` `serialize()`, which invokes each block's `save()`) run in Node against fixture attribute sets — not `serialize_block()`. Render-test-only (Q6 option B) is still rejected for the gap-fillers (defers a preventable defect), but the pattern blobs sidestep the *per-attribute serialization* problem for the pinned target version. They do **not** confer immunity to cross-version drift: a hand-authored blob is stored block markup like any other, so WordPress's editor-load byte-compare re-runs `save()` against it on a non-6.6 install with the same force it applies to generated markup. So Q9 (version coverage) bites the blobs equally, not just the gap-fillers.

> **Decision log (2026-05-27):** serialization = pre-serialized pattern blobs (token/slot substitution, no per-attribute serialization) for covered regions + byte-exact parity for the small free-tree gap-filler set, oracle = JS `@wordpress/blocks` `serialize()` (runs `save()`), NOT `serialize_block()`. Corrected in iteration 7 after the review showed `serialize_block()` tests the wrong layer. Note: using the JS serializer as oracle re-touches the §4.2.1 "language-portable" stance — acceptable since ADR-0001 fixes the language as Node/TS, where `@wordpress/blocks` is available. Risk accepted: parity fixtures must cover the attribute *combinations* the gap-filler actually emits, not one set per block. Cross-version drift — for the gap-fillers **and** the hand-authored pattern blobs alike — is **Q9**; the seed blobs must be CI-parser-validated against the pinned 6.6 `save()` oracle before "already-byte-correct" is claimed for them.

### 6.3 Idempotency & reproducibility

Same IR → byte-identical `.zip`, on any machine, any run. Requirements: (a) JSON emitted with sorted keys and stable formatting; (b) deterministic file ordering in the archive; (c) fixed archive timestamps (a constant epoch, not "now") so the zip's mtime metadata does not vary; (d) no host-dependent values (no absolute paths, no locale-dependent formatting). Reproducibility is what makes the assembler testable — a golden-file test asserts the exact bytes for a fixture IR.

### 6.4 User-string handling and injection defense

The brief explicitly requires the ADR to cover "handling user-provided strings in theme data." User strings (theme slug, title, author, description, block `text`, design-token values) and AI strings flow into multiple output contexts, and **HTML-escaping is correct for only one of them** (block text). Treating "we escape text" as a blanket defense is wrong: each context has its own escape contract, and the assembler must apply the right one per context. This is an assembler responsibility (§6.1), enforced at write time, not something the IR schema alone can close.

| Output context | Vector if unescaped | Required transform |
|---|---|---|
| Block `text` → HTML element content | `<div>`/`<script>` injection | HTML-entity encode (already in §2.2) |
| URL-valued attributes (`core/social-link.url`, `core/button.url`, `core/image.url`/`href`) → rendered anchor `href` | a `javascript:`/`data:` URL → **stored XSS** (HTML-entity encoding does *not* neutralize it — the string carries no HTML-special chars) | validate against a safe-scheme allowlist (`https:`, `http:`, `mailto:`, `tel:`) in the §4.2 overlay; reject any other scheme |
| `title`/`author`/`description` → `style.css` comment header | a `*/` closes the comment → raw CSS/PHP injected; a newline injects a fake header field (`License URI: javascript:…`) | strip/reject `\r`, `\n`, and `*/` before writing |
| Design-token values → `theme.json` → CSS custom properties | a color like `#f00; } body{…}` injects CSS the style engine emits verbatim | per-category value validation: hex-color regex for colors, number+unit for sizes, font-family safe-list — added to the `designTokens` schema (layer-3) |
| Strings → `patterns/*.php` comment header **or** body | `*/ ?><?php system(…) ?>` → **RCE**: pattern files are `require`d by WordPress, so they execute, not just parse | strip/reject `?>`, `<?`, `<?php`; assemble PHP pattern files with **no string interpolation** of user/AI data into PHP context (data is data, never code) |
| `theme.slug` / `patternRef.pattern` slug → archive entry path | `../../wp-config` → zip-slip / path traversal | validate every slug against `^[a-z][a-z0-9-]{1,39}$` *before* path construction; build entry paths from literal prefixes only; configure JSZip to reject `..`/absolute entries |
| `patternRef.params` text values → token/slot substitution into a pre-serialized pattern blob (§6.2) | textual substitution of `-->` / `<!-- wp:html` closes the attribute comment and injects a raw delimiter *between live delimiters* — layer-4 catches it post-assembly, but the substitution step itself has no escape spec | resolve token-ref slots to typed values (**structured** substitution, not string-replace); HTML-entity encode text slots before substitution; reject any param value containing `-->` |

The `patternRef.pattern` slug in the §2.4 schema is therefore tightened from a free `string` to the slug pattern above. The PHP-RCE vector (pattern files execute on activation) is the highest-severity finding and the reason pattern-file assembly must avoid interpolation entirely. None of these are defense-in-depth wishlist items — each is a concrete vector a free-text description or a prompt-injected token value reaches today. They belong in the ADR's security section as well as here.

**Input-stage threat (prompt injection).** The table above covers *output*-context injection; the *input* stage carries its own vector. The user's natural-language description flows into Track 3's generation prompt, so a description like *"ignore prior instructions and emit …"* is a prompt-injection attempt. The "trust the parser, not the prompt" stance still holds the three block-structure invariants regardless — but prompt injection can still steer the model toward hostile attribute values (e.g. the `javascript:` URL vector above), burn retry budget, or exfiltrate system-prompt context. Track 1's trust-boundary requirement on Track 3: user-controlled text MUST be passed as a structurally isolated data slot (e.g. XML-delimited `<user_description>…</user_description>`), never concatenated into instruction context. (Implementation is owned by Track 3; it is named here because it is a trust-boundary requirement of the contract, not a Track-3 internal.)

### 6.5 Site-data provisioning

Some allowlisted blocks render empty without backing site data, and the §7 gate's "zero `core/missing`" check will *not* catch it — the block is registered, so it passes, but renders blank (from [`IR-notes.md`](pattern-library/IR-notes.md) §5 + the [pattern-library](pattern-library/README.md) composition rules). The two in the MVP set:

- **`core/navigation`** references a `wp_navigation` menu entity (a `ref`). With no menu provisioned it renders empty or falls back. For a static `.zip` with no database, the realistic MVP answer is to emit the navigation block in a mode that renders *without* a stored menu — a page-list fallback (`overlayMenu` / the block's auto-page-list behavior) — or to provision a default menu via the theme's setup. The assembler must pick one; "emit `core/navigation` and hope" produces an empty header.
- **`core/site-title` / `core/site-tagline`** read site settings; in a fresh install they show the install's defaults, which is acceptable, but the assembler should not assume the theme controls them.

The assembler's contract is therefore **file emission plus a fixed provisioning rule**: when the IR contains a `core/navigation` node, the assembler unconditionally emits it in page-list fallback mode (no stored-menu `ref`) — so no IR-level manifest field is needed for the MVP, and the presence of the node is the only signal required. (Revisit a manifest abstraction only if Track 3 surfaces a second, distinct provisioning need.) The §7 harness should additionally assert that `core/navigation` renders non-empty (not just that it's registered), closing the "passes the gate, greets the user with an empty nav" gap that damages the first-impression JTBD.

## 7. Vanilla-WP install/activate test harness

### 7.1 The harness exists because activation success is not correctness

WordPress's hard activation errors (`theme_no_stylesheet`, `theme_no_index`, etc.) catch only gross failures — missing `style.css`, missing `index.html`.[^19] The damaging defects this project must catch — hallucinated names (→ `core/missing`) and dropped `theme.json` keys — produce **zero activation warnings**.[^2][^11] So "installs and activates" is necessary but nowhere near sufficient; the harness must inspect post-activation state.

### 7.2 Recommended harness: WordPress Playground (headless) — Q5 RESOLVED

`@wp-playground/cli run-blueprint` runs a headless, serverless WordPress and exits — CI-friendly, no Docker, no hosted instance, honoring the standalone constraint.[^21] A blueprint installs the generated `.zip` (`installTheme` with `activate: true`), then uses the `runPHP` step to assert correctness the platform won't:[^22]

```jsonc
{
  "$schema": "https://playground.wordpress.net/blueprint-schema.json",
  "preferredVersions": { "wp": "6.6", "php": "8.2" },   // pinned to the §3.2/§6.2 target
  "steps": [
    { "step": "installTheme",
      "themeData": { "resource": "vfs", "path": "/tmp/out/theme.zip" },
      "options": { "activate": true } },
    { "step": "runPHP", "code": "<?php require '/wordpress/wp-load.php'; echo gate_assertions();" }
  ]
}
```

(The blueprint runs the zip from `vfs` — the harness must first write the assembled `.zip` into Playground's virtual filesystem, e.g. a `writeFile`/mount step placing it at `/tmp/out/theme.zip`, or `installTheme` reports "resource not found.") The `runPHP` gate is where correctness is actually proven — four assertions, each targeting a silent failure the platform won't surface:

1. **Activation** — `wp_get_theme()->errors() === false` and the active stylesheet matches our slug. Catches the hard `WP_Theme::errors()` class (§7.1) WP-CLI already catches, kept for completeness.[^19]
2. **Zero `core/missing` AND zero undelimited raw HTML** — for every `templates/*.html` and `parts/*.html`, run `parse_blocks()` and walk the tree, *skipping `blockName === null` whitespace nodes*. Assert every non-null `blockName` resolves via `WP_Block_Type_Registry::get_instance()->is_registered()` (catches the hallucination that parsed fine, §4.1), assert no `blockName === 'core/html'`, **and assert no non-whitespace `blockName === null` chunk** — raw HTML *without* a delimiter parses as a freeform null-named chunk, not `core/html`, so the §5 layer-4 `wp:html` scan would miss it; this is where the render gate backstops undelimited HTML (the actual Bossenger failure mode[^38]).[^2]
3. **Zero dropped `theme.json` keys** — construct a fresh `WP_Theme_JSON($raw_decoded, 'theme')`, take `get_raw_data()`, and deep-diff against the decoded input, **excluding keys that WordPress relocates during v2→v3 migration** (those are moves, not drops, and would false-positive). Any key present in input but absent (and not relocated) in `get_raw_data()` was silently dropped (§3, the §2.4 hazard).[^11]
4. **`core/navigation` renders non-empty** — if the theme uses `core/navigation`, render the header and assert the output is non-empty (§6.5) — "registered but renders blank for lack of a menu entity" passes assertion 2 but fails the user.

"Zero warnings or errors" is thus operationalized, not hand-waved: **activation clean AND zero `core/missing` AND zero `core/html` AND zero undelimited-HTML chunks AND zero dropped `theme.json` keys AND non-empty navigation.** The gate returns a non-empty failure list → CI fails with the structured §5.2 errors attached.

> **Decision log (2026-05-27, v1):** install/activate harness = WordPress Playground `run-blueprint` (headless wasm) as the default and only required gate; WP-CLI-in-Docker is an *optional* deeper-fidelity job, not on the critical path. Alternatives rejected: hosted WP (violates the standalone constraint — external credentials), Docker-as-default (adds a heavy dependency to "minimal-setup local run," contradicting the brief). Risk accepted: Playground's wasm runtime can diverge subtly from a real LAMP install; **Q9** (WP-version coverage) tracks the residual exposure and the optional Docker job is the escape valve if divergence ever bites. Standalone constraint (`STRATEGY.md`) was decisive.

### 7.3 CI integration

The harness runs on every PR that touches the assembler, the allowlist, the serializer, or fixtures. The pre-package validators (§5) are the fast inner gate (milliseconds, no WordPress); Playground is the slower outer gate (seconds, real WordPress). WP-CLI alone is insufficient — it returns non-zero only on hard activation failure, not on silent corruption.[^20] Theme Check is a `.org`-compliance lint (header completeness, deprecated functions), useful as a third layer but not a block-grammar validator.[^24]

## 8. Contract exposed to Track 3 (AI orchestration)

### 8.1 What the AI sees

- **The IR JSON Schema** — the shape the model targets. This is the seam that keeps the integration provider-agnostic: any provider's structured-output mechanism (OpenAI Structured Outputs' FSM-constrained sampling, Anthropic strict tool use, or constrained decoding via llguidance/XGrammar) targets the *same* IR.[^29][^30][^31][^33] Track 1 publishes the schema; Track 3 chooses the mechanism. **Reconciliation with [ADR-0001](adr/0001-application-stack.md):** the ADR commits to the Vercel AI SDK's `generateObject` + Zod, where "the same schema powers `generateObject` and validates the IR." That holds for the **non-recursive envelope** (`theme`/`tokens`/`regions`-metadata), but per Q7 the recursive block tree (`content`) cannot be enforced by hosted strict mode (Anthropic strict tool use forbids recursive schemas[^31]). So the seam splits: `generateObject` strict-validates the envelope; the recursive `content` is generated as best-effort JSON and enforced *only* by the §5 post-hoc validator — which is exactly "trust the parser, not the prompt." An implementer reaching for `generateObject({ schema: fullRecursiveIrZod })` will hit a provider-side rejection or silent constraint-stripping; the envelope/content split is the intended shape. (One sentence to add to ADR-0001 so the two docs stop disagreeing: "`generateObject` strict-validates the IR envelope; the recursive block tree is enforced by the §5 validator, not at generation time.")
- **The block-name allowlist + attribute schemas** — injected into the model's context so it selects from real blocks, the same way Text-to-SQL systems inject the table/column list before generation. The allowlist constrains generation; the validator enforces regardless.
- **The pattern catalog references** (slugs + parameters), owned by Track 2, surfaced through the IR's pattern-reference node (§2.3).

### 8.2 How validation errors feed back for retry

On validation failure the orchestrator receives the structured error list (§5.2) and constructs a retry re-prompt. The contract is **both layered** (Q4 resolved): stable `code` + `path` for the orchestrator's retry logic, plus the human-legible `hint`/`message` to steer the model. Structured codes alone starve the model of correction context; free-form re-prompts alone leak validator internals and resist branching — the layered format dominates both because each consumer reads only the fields it needs. The *retry budget and policy* are Track 3 internals and out of scope here; Track 1 only guarantees the error list is well-formed and complete.

> **Decision log (2026-05-27, v1):** error-feedback contract = both-layered (machine `code`/`layer`/`path`/`invariant` + bounded ≤200-char NL `hint`), field set frozen in §5.2. Alternatives rejected: codes-only (starves the model → lower first-try recovery), NL-only (leaks internals, breaks the §8.3 boundary, unbranchable). Risk accepted: `hint` quality is unmeasured until Track 3's retry loop exists; the field is optional so a weak hint degrades to codes-only rather than failing. Surfaced in its place: **Q7**.

### 8.3 What the AI must NOT see

Raw JSON Schema validation dumps (AJV's verbose error objects), validator internals, the vendored `theme.json` schema diffs, and IR-implementation churn. Leaking these couples the model's behavior to our internals and makes the seam brittle. The orchestrator sees the *published* IR schema and the *structured* error format — nothing else. This boundary is also what lets the *Validator escape-attempt trend* metric work: Track 1's parser instruments the count of caught escape attempts (the data source), and Track 3 owns the metric — a clean producer/consumer split that only holds if the internals stay hidden.[^STRATEGY]

## 9. Open architectural questions

Each names ≥2 genuine alternatives, the invariant/metric at stake, and a recommendation or `[unresolved]` with the evidence needed. **8 of 10 are resolved** (decision logs in the body sections); the 2 that remain (Q7, Q9) are genuinely cross-track and correct to leave open in a Phase-1 PRD — they resolve when Track 3's generation experiment runs (Q7) and when cross-version `save()`-churn data exists (Q9).

### Q1 — IR shape: free block-tree vs. pattern-composition vs. hybrid *(component: IR)* — RESOLVED

Hybrid: `patternRef` is the default authoring mode; constrained `blockNode` free-tree is reserved for uncovered gaps. Unblocked by the Track 2 seed ([`pattern-library/`](pattern-library/) + [`IR-notes.md`](pattern-library/IR-notes.md)), whose `meta.json` parameterizable/locked split demonstrates the pattern-reference + slot model. See §2.3 decision log. Residual (Track 3, not Track 1): the policy governing when a free-tree is allowed vs. a pattern forced.

### Q2 — `theme.json` schema source *(component: theme.json)* — RESOLVED

Vendor the upstream draft-07 schema, pinned by commit; validate with AJV. See §3.1 decision log. Replacement question surfaced: **Q6**.

### Q3 — Block-validation authority *(component: validator)* — RESOLVED

Standalone allowlist + containment grammar as the fast inner gate; Playground `parse_blocks()` as the authoritative outer backstop. See §4.2.1 decision log. Replacement question surfaced: **Q8**.

### Q4 — Error-feedback contract for retry *(component: Track 3 seam)* — RESOLVED

Both-layered: machine `code`/`layer`/`path`/`invariant` + bounded ≤200-char NL `hint`, field set frozen in §5.2. See §8.2 decision log. Replacement question surfaced: **Q7**.

### Q5 — Install/activate harness *(component: harness)* — RESOLVED

WordPress Playground `run-blueprint` (headless wasm) as the default/required gate; WP-CLI-in-Docker optional deeper-fidelity job. Decisive factor: the standalone constraint. See §7.2 decision log + the three-assertion gate. Replacement question surfaced: **Q9**.

### Q6 — Serialization parity *(component: assembler/serializer)* — RESOLVED

Pre-serialized pattern blobs (token/slot substitution) for covered regions + byte-exact parity for the small free-tree gap-filler set, oracle = JS `@wordpress/blocks` `serialize()` (not `serialize_block()`, corrected iteration 7). See §6.2 decision log.

### Q7 — Recursive IR vs. structured-output constraints *(component: IR ↔ Track 3 seam; surfaced v1 by §2.4)*

The IR's block tree is recursive and routinely exceeds 5 nesting levels, but OpenAI Structured Outputs forbids recursion and caps nesting at 5,[^29] and Anthropic strict tool use forbids recursive schemas.[^31] So the seam's assumption that "any provider's structured-output mode targets the same IR" (§8.1) does not hold for the recursive core. Options:

- **A. Constrained decoding via a CFG engine** (llguidance/XGrammar) instead of provider strict mode. These support full context-free grammars including recursion,[^33] so the IR is enforceable at generation time — but they require self-hosting/open-weights inference, which conflicts with the brief's "swap a hosted provider" expectation and adds ops weight.
- **B. Non-recursive IR encoding** — flatten the tree into a node array with explicit parent IDs (an adjacency list), which fits strict mode's flat-object limits; the assembler reconstructs the tree. Keeps hosted strict mode usable; shifts complexity into the assembler and makes the IR less human-legible.
- **C. Strict mode for the flat envelope + post-hoc validation for the tree** — the provider strict-mode-validates `theme`/`tokens`/`regions` metadata, and the recursive `content` is emitted as model-best-effort JSON that the §5 layer-1 validator checks (no generation-time guarantee on the tree, full enforcement at the gate).
- **At stake:** the provider-swappability seam (A breaks hosted-provider swap; B/C preserve it), *first-try generation success rate* (A/B highest — generation-time guarantee; C relies on retry), and the catch invariant (all three safe — §5 enforces regardless). **Lean: C as default** (honors "trust the parser, not the prompt" — the gate is authoritative anyway, so a generation-time guarantee on the tree is belt-and-suspenders), **with B reserved if first-try success proves too low under C.** **`[unresolved]`** — needs a first-try-success measurement of free-tree generation under hosted strict mode (envelope-only) vs. the flattened encoding, which is a Track 3 experiment gated on the §2.4 schema freezing.

### Q8 — Per-block attribute-schema sourcing *(component: allowlist/grammar)* — RESOLVED

Extract the key/type surface from core `block.json` at build time + a thin hand-authored value-range overlay. Confirmed by inspection: `core/heading` `block.json` carries typed attributes but no `level` range.[^45] See §4.2 decision log.

### Q9 — WP-version coverage: single pinned target vs. matrix *(component: assembler/harness; surfaced v1 by §6.2 + §7.2)*

The serializer is pinned to one WP version (6.6) for byte-exact `save()` parity (§6.2), and the harness tests against that one version (§7.2). But users install the generated theme into whatever WordPress they run — 6.5, 6.7, 6.8+. Because `save()` markup drifts across releases,[^5] a theme that is invalidation-free on 6.6 can show "attempt recovery" on a later version, and a `theme.json` `version: 3` feature may behave differently on an older release.

- **A. Single pinned target (6.6).** Declare it honestly via `style.css` `Requires at least` / `Tested up to`,[^17] test one version in CI, accept that newer/older installs are best-effort. Cheapest; narrowest guarantee.
- **B. Version matrix in CI** — run the §7.2 blueprint against, say, minimum-supported + 6.6 + latest, and only ship markup that is invalidation-free across all three. Strongest guarantee for real users; multiplies CI time and may force the serializer toward a markup subset that round-trips cleanly on every tested version.
- **C. Pin + drift detector** — single target, plus a scheduled job that re-runs the fixture corpus against the newest WP release and alerts on new invalidation (the §3.3 drift pattern applied to serialization).
- **At stake:** the *install/activate cleanliness* metric **as users actually experience it** (not just on our pinned version) vs. CI cost and serializer flexibility. **Lean: A for the MVP** (the brief targets "vanilla WordPress," singular; honest version headers set expectations) **+ C as a lightweight guard**, escalating to B only if real installs show cross-version invalidation. **`[unresolved]`** — needs data on how often core `save()` output actually changes for the MVP block set across recent releases (low churn → A is safe; high churn → B is forced).

### Q10 — Proving the invariant against unseen escapes *(component: validator/test strategy)* — RESOLVED

Layered: curated corpus (per-PR deterministic gate) + property-based tests asserting the invariant as a checkable property over generated IRs + periodic adversarial red-team feeding findings back into the corpus. See §5.3 decision log.
